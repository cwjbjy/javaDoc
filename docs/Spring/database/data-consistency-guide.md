# 数据一致性入门：从一次 CRUD 到可靠的业务操作

这份指南面向已经会写 Java、Spring 和基础 CRUD，但还没有系统处理并发、事务和重试的开发者。读完后，你应当能为一个写接口回答：**必须保持什么业务规则，哪些执行顺序会破坏它，以及由谁保证它。**

## 1 先写业务规则，再选技术

"数据一致"首先是一句可以验证的业务承诺，而不是一个注解。

例如，为一个订单和账户系统可以写下这些规则：

| 操作             | 完成后必须成立的规则                                               |
| ---------------- | ------------------------------------------------------------------ |
| 修改订单收货地址 | 订单中的商品明细和应付金额不应被旧数据覆盖                         |
| 增加账户余额     | 每次有效业务操作的增量都保留下来                                   |
| 跨账户转移库存   | 假设初始数据合法，转移成功后库存只存在于目标账户；失败后仍在源账户 |
| 创建账户         | 如果业务规定账号唯一，不能出现两个相同账号的账户                   |
| 删除订单         | 已删除的订单不再被查询到；其独占的附件最终能够被回收               |
| 重试同一业务请求 | 如果接口承诺幂等，同一请求不能产生两次业务效果                     |

接着区分几个各司其职的概念：

| 概念       | 它回答的问题                                     |
| ---------- | ------------------------------------------------ |
| 原子性     | 一个操作会不会只完成一半？                       |
| 并发控制   | 两个操作交错执行时，会不会覆盖或违背彼此的结果？ |
| 事务       | 多个数据库操作能否作为一个整体提交或回滚？       |
| 唯一约束   | 不论哪个应用实例写入，数据库能否拒绝重复值？     |
| 幂等性     | 同一业务操作重复执行，是否只产生一次预期效果？   |
| 最终一致性 | 暂时不一致以后，是否有可靠机制使状态收敛？       |

这些能力需要组合使用。事务不会自动识别重复请求，原子操作不会自动保证"一张订单只扣款一次"，日志也不会自动重试失败的文件删除。

## 2 为什么先查再保存会丢数据

### 2.1 单线程正确，不代表并发正确

常见写法是：查询订单、修改状态、保存整个对象。它很直观，但对象可能在内存中停留一段时间，随后把数据库里更新过的字段覆盖回旧值。

下面是交错执行的示意时间线；A、B 是两个请求，初始库存数量为 10。

```text
时间    请求 A：修改订单状态           请求 B：增加库存数量
t1      读订单，关联库存数量为 10
t2                                    将库存加到 11
t3      修改内存对象中的订单状态
t4      保存整个旧对象，库存又变成 10
```

两个请求都可能返回成功，最终却少了一次库存增量。这叫"丢失更新"。问题在于：A 只想修改订单状态，却把旧的库存数量一起写了回去。

### 2.2 只写本次负责的字段

解决方案是使用局部更新，只修改本次操作负责的字段，而不是保存整个对象。

示意片段（伪代码）：

```java
// 修改订单状态时，只更新状态字段，不携带关联的库存数据。
repository.updateField(orderId, "status", newStatus);

// 在数据库当前值上累加，不在 Java 中执行"读出 + 1 + 保存"。
repository.incrementField(accountId, "inventory.quantity", 1);
```

核心原则是：每个写操作只触碰自己负责的字段，不要把读到的旧数据整体写回去。大多数数据库对单条记录的更新是原子的，但"先查询，再单独更新"是两个操作，不能因为每一步单独原子，就认为整个过程原子。

> 在具体数据库中如何实现局部更新？参见 [MongoDB 实现篇：局部更新](data-consistency-mongodb-guide.md#2-局部更新与丢失更新)。

### 2.3 局部更新也有边界

两个请求分别将订单状态改成 A 和 B，使用局部更新仍可能由后完成的写入覆盖前者。这是否允许，取决于业务。

如果需要拒绝旧页面提交的修改，可以使用版本号进行条件更新，通常称为乐观锁或 CAS（比较后更新）：

1. 读取时得到版本 7。
2. 更新条件同时包含 `id` 和 `version = 7`。
3. 更新字段时把版本增加到 8。
4. 若没有匹配记录，报告冲突，让调用方重新读取并决定如何合并。

版本字段必须真正参与所有相关写路径；只给某个实体加注解，却让其他自定义更新绕过版本条件，不能构成完整保护。

`synchronized` 只约束当前 JVM 内、使用同一把锁的代码。应用部署为多个实例，或还有脚本直接写库时，它不能代替数据库层的并发控制。

## 3 写入没有报错，为什么还要检查结果

执行一条更新语句不等于找到了业务对象。数据库可以合法地返回"匹配 0 条"，而不抛异常。

对于需要确认结果的业务，应检查写入结果：

| 结果                       | 含义                         | 常见处理                                   |
| -------------------------- | ---------------------------- | ------------------------------------------ |
| 匹配数 = 0                 | 条件没有匹配记录             | 按条件含义判定不存在、版本冲突或状态不允许 |
| 匹配数 = 1，实际修改数 = 0 | 找到了记录，但值可能没有变化 | 相同值更新通常可以视为成功                 |
| 匹配数 = 1，实际修改数 = 1 | 找到了记录并发生修改         | 继续业务流程                               |
| 删除数 = 0                 | 本次没有删除记录             | 明确接口是否允许"重复删除也成功"           |
| 预期一条却匹配多条         | 唯一性假设被打破             | 报告数据异常；事务内阻止提交               |

示意片段（伪代码）：

```java
UpdateResult result = repository.update(condition, changes);
if (result.getMatchedCount() != 1) {
    throw new IllegalArgumentException("对象不存在或更新条件不满足");
}
```

这样可以避免"目标不存在，接口仍返回更新成功"。但匹配数本身不能准确区分所有业务原因，错误消息仍应与查询条件一致。

还要区分"写入失败"和"没有收到确认"。网络超时时，操作可能已经完成，只是响应没有送达；不能直接把超时理解为"肯定没写进去"，然后无条件重复操作。第 6 节会处理这个问题。

## 4 多次写入如何一起成功或失败

### 4.1 调整顺序不能解决跨记录原子性

库存转移涉及源账户和目标账户两条记录。没有事务时，两种顺序都有失败窗口。

示意时间线：这里的"失败"指第二步未完成，且没有可靠补偿。

```text
先从源扣减库存 → 写入目标失败 → 库存丢失
先向目标追加   → 扣减源失败   → 库存重复
```

"先校验源和目标都存在"只能改善错误提示。校验之后，另一个请求仍可能删除或修改它们。

### 4.2 把一次业务操作放进同一个事务边界

解决方案是将整个业务操作放在同一个事务中。

以下为流程示意：

```text
开始事务
  读取源账户和目标账户
  校验源余额充足
  向目标追加库存，检查操作结果
  从源扣减库存，检查操作结果
提交事务
  任一步失败：回滚本次事务内的所有数据库写入
```

这能保证事务内多条记录的写入一起提交或回滚，但不意味着任意分开的读取都能获得同一个快照。需要一致读取视图的读流程，也必须明确自己的读取方式和事务边界。

类似地，给多个账户增加余额时，如果业务承诺"全部成功或全部失败"，就需要将这些更新组合到事务中。批量 API 或循环调用都不天然提供跨记录的整体原子性。

> 在具体数据库中如何配置和使用事务？参见 [MongoDB 实现篇：事务配置](data-consistency-mongodb-guide.md#5-事务配置与使用)。

### 4.3 事务生效的通用条件

不论使用哪种数据库，事务生效都有一些共性要求：

- 数据库本身必须支持多记录事务。
- 参与事务的操作必须使用同一个会话或连接。事务管理器通常将会话绑定到当前线程；随意切换异步线程或使用独立客户端，可能脱离事务。
- 不要捕获异常后直接返回"成功"。事务回调必须把失败传播出去，或明确标记回滚。
- 事务应尽量短，避免把网络调用、文件 IO 和长时间计算放进事务。

### 4.4 事务失败以后，不要盲目重试

并发写冲突可能需要重新执行整个事务；提交结果未知时，则可能需要确认或重试提交。这是两种不同情况。

应依据数据库驱动的错误类型决定重试范围，限制次数并设置退避；回调中也应避免邮件、文件删除等不可随数据库回滚的副作用。

如果使用声明式事务注解，还要考虑代理调用和回滚规则，不能只把注解贴到方法上。通用机制可参阅 [Spring 事务指南](../spring-transaction-guide.md)。

## 5 唯一性为什么必须交给数据库

### 5.1 查询不存在，只能说明查询的那一刻不存在

创建账户前查询账号是否存在，无法阻止两个请求同时创建同账号的账户。

示意时间线：两个请求创建账号 `A001`。

```text
请求 A：查询，不存在 ───────────────→ 插入成功
请求 B：        查询，不存在 ───────────────→ 也插入成功
```

应用可以保留预检查，提供更友好的提示，但最后必须由数据库的唯一索引拒绝竞争中的重复写入，并把重复键异常转换为合适的业务响应。

事务也不会自动给"账号必须唯一"建立约束。事务解决多个操作的提交边界，唯一索引解决所有写入方都不能破坏的唯一性规则。

### 5.2 注解和配置不等于数据库实际状态

在实体类上声明唯一索引注解，不证明数据库已经创建了对应索引。需要确认：

- 数据库是否已启用自动索引创建，或是否通过迁移脚本手动执行过建索引命令。
- 实际集合上的索引是否与预期一致（字段、方向、`unique` 标志）。

> 在具体数据库中如何核验索引状态？参见 [MongoDB 实现篇：唯一索引管理](data-consistency-mongodb-guide.md#6-唯一索引管理)。

### 5.3 已有数据上的索引需要发布计划

建立唯一索引之前，先检查已有重复值、缺失值，并定义字段是否去首尾空格、是否区分大小写。普通唯一索引不会自动完成业务要求的全部规范化。

已有重复数据可能导致建索引失败。应先制定数据处理方案，再通过可追踪的迁移步骤发布索引并验证结果。不要为了让启动成功，直接删除重复业务数据或随意删掉现有索引。

## 6 原子操作为什么仍然会重复计数

数据库的原子累加可以防止两个不同的有效增量相互覆盖，却无法判断两个请求是不是同一件事。

示意时间线：一次业务操作需要扣款 100 元。

```text
客户端提交请求 → 服务端将余额从 1000 减到 900 → 响应在网络中丢失
客户端重试     → 服务端将余额从 900 减到 800   → 客户端收到成功
```

每次更新都原子，最终仍然多扣了一次。列表内去重只能防止一个请求携带重复项；不能防止同一个请求发送两次。

如果扣款必须对应"一次订单事件"，应使用稳定的业务标识或幂等键。调用方重试时复用同一个键，服务端在明确的作用域内处理它，例如"用户 + 操作类型 + 请求键"。

以下为推荐方案的流程示意：

```text
收到请求：幂等键 K、业务参数 P
开始事务
  插入幂等记录 K（数据库唯一约束），记录参数摘要
  执行业务写入
  保存本次结果到幂等记录
提交事务

相同 K 再次到达：
  已完成且参数一致 → 返回已保存结果
  参数不同         → 拒绝复用该键
  首次请求尚未完成 → 明确返回处理中或按策略稍后重试
```

唯一约束负责处理同时到达的同键请求；在发生重复键错误后，应退出失败的事务，再读取已提交结果，而不是继续使用已失败的事务执行写入。

幂等记录不能先独立提交，再执行业务操作，否则可能出现"记录说处理过，业务却没有完成"。也不能先执行业务操作，再保存记录，否则中间崩溃后重试仍会重复执行。

记录的保存期限必须覆盖业务允许的重试窗口；过早过期后，同一个旧请求仍可能再次生效。对于订单等长期业务事件，永久业务唯一标识往往比短期请求缓存更可靠。

> 在具体数据库中如何实现幂等记录？参见 [MongoDB 实现篇：幂等记录](data-consistency-mongodb-guide.md#7-幂等记录的-mongodb-实现)。

## 7 数据库和外部资源如何保持一致

### 7.1 数据库事务不能回滚外部资源

删除订单涉及两种资源：数据库中的记录和磁盘上的附件文件。

| 顺序                 | 中途失败可能留下的状态             |
| -------------------- | ---------------------------------- |
| 先删除文件，再删记录 | 记录仍在，但指向的文件已不存在     |
| 先删记录，再删除文件 | 记录已删除，磁盘留下无人使用的文件 |

通常优先保证仍被引用的资源可用，再处理暂时遗留的文件。但后者要成为可靠方案，还必须有后续清理机制。

### 7.2 原子取得被删除数据再清理

比较好的做法是：使用原子操作移除记录并取得修改前的完整数据，再依据真实记录中的文件路径执行清理。这避免了直接相信客户端提供的旧路径，也让数据库删除结果与用于清理的数据来自同一次操作。

但如果更新流程仍先读取旧文件路径，再更新数据库，两个步骤不是同一个原子操作。例如两个请求都读到旧文件 A，一个写入 B，另一个写入 C，随后它们都只清理 A，B 可能成为遗留文件。

如果文件地址允许共享或重新使用，还需要定义所有权与引用规则：某条记录删除后，该文件可能仍被其他记录使用。仅知道"这是本次记录的旧文件"不足以证明"现在可以安全删除"。

### 7.3 最终一致性需要一条可靠的恢复路径

文件删除失败时只记录日志，日志有助于诊断，但进程不会因为记了日志就自动完成清理；数据库操作完成后、调用删除文件之前崩溃，也可能没有任何清理日志。

一种可演进的方案是持久化清理任务，也叫 outbox：把"需要删除哪个对象"作为待处理数据保存，使进程重启后仍能找到它。

```text
数据库事务内：
  删除记录或替换文件引用
  写入待清理任务（对象键、状态、重试信息）
共同提交
        |
        v
后台清理器读取任务
  确认对象满足删除条件
  删除文件（文件已不存在也视为完成）
  标记任务完成
失败则保留任务，退避重试并在持续失败时告警
```

进程若在删文件后、标记任务前崩溃，任务会重复执行，因此删除必须幂等。任务与业务变更共同提交，可以避免业务已经提交却丢失清理意图。

"确认无人引用，再删除"本身也可能有并发窗口。比较容易控制的方案是使用不可复用的对象键，并明确独占所有权；允许共享时，需要统一的引用管理或删除状态协议，而不能只做一次普通查询。

上传新文件后、数据库引用保存前也可能崩溃，留下另一类孤儿文件。可以给临时上传设置过期回收机制。数据库删除后的 outbox 并不能覆盖上传阶段的所有故障。

> 在具体数据库中如何实现 outbox 清理？参见 [MongoDB 实现篇：跨资源一致性](data-consistency-mongodb-guide.md#8-跨资源一致性数据库与文件)。

## 8 如何测试真正可能出错的地方

### 8.1 单元测试证明调用约定，集成测试证明数据库行为

Mock 测试可以证明"代码进入事务回调""条件不匹配会抛异常""没有调用旧的整对象保存方法"，但不能证明：

- 数据库服务端支持事务；
- 第二次写入失败后第一次真实写入已回滚；
- 数据库已经建好唯一索引；
- 两个真实并发请求不会互相覆盖。

使用模拟的事务管理器和仓储的测试，不能替代"目标已写入，删除源时失败"的回滚测试。应用上下文启动成功也不能作为真实数据库事务能力的证明。

### 8.2 把断言写在最终状态上

推荐在隔离的、支持事务的数据库测试环境中覆盖以下场景。它们是待执行的测试设计。

| 场景               | 如何制造故障或交错                     | 必须断言的最终状态                   |
| ------------------ | -------------------------------------- | ------------------------------------ |
| 账户改名与余额并发 | 用屏障或 `CountDownLatch` 控制读写顺序 | 新名称保留，余额增量也保留           |
| 库存转移中途失败   | 在目标追加成功后、源扣减前抛异常       | 源仍有库存，目标没有新增副本         |
| 并发创建同编号账户 | 两个请求同时通过预检查                 | 最终只有一条记录，失败方得到约定错误 |
| 相同值更新         | 把状态再次更新为原值                   | 匹配成功可正常返回，不误报不存在     |
| 对象消失           | 查询后由另一请求删除对象               | 写入结果被识别，不返回虚假成功       |
| 响应丢失后重试     | 首次已提交，同一幂等键再次请求         | 在实现幂等后，业务增量只发生一次     |
| 文件清理失败       | 文件删除抛 IO 异常                     | 在实现持久化清理后，任务仍在且能重试 |
| 提交后进程崩溃     | 数据库提交后、清理前停止进程           | 重启后能发现待清理任务               |

测试应从合法初始数据出发，同时单独覆盖历史脏数据。不要只断言返回字符串为"成功"，要查询最终记录数量、字段值和任务状态。

不要依靠固定 `sleep` 让两个线程"碰巧撞上"；控制关键时刻的先后关系，测试才能重复。压力测试可以提高发现问题的概率，但不能替代可重复的故障注入与状态断言。

### 8.3 三个自测问题

1. 一个请求给三个商品扣库存，第三个不存在，前两个该保留扣减吗？
2. 更新状态后匹配数 = 1、实际修改数 = 0，一定失败了吗？
3. 文件删除失败只写日志，能否称为有保证的最终一致性？

参考答案：第一题先看契约；如果承诺整体成功，应在事务中回滚前两个，允许部分成功则应明确返回逐项结果。第二题不一定，相同值更新可能没有实际修改。第三题不能，缺少可恢复的清理意图和重试机制，状态可能永远不收敛。

## 9 开发时的选择速查

| 你面对的问题             | 优先考虑                         | 它不能单独解决什么             |
| ------------------------ | -------------------------------- | ------------------------------ |
| 修改单记录中几个字段     | 局部更新（只写变更字段）         | 同一字段的旧值覆盖             |
| 在当前数值上累加         | 原子操作（数据库端累加）         | 同一业务请求重复提交           |
| 只允许基于指定旧状态修改 | 条件更新、版本号                 | 所有写路径未遵守同一协议的情况 |
| 多条记录必须共同成功     | 数据库事务                       | 文件、邮件等外部资源回滚       |
| 名称或业务编号不能重复   | 实际生效的唯一索引               | 自动规范化业务输入             |
| 请求重试只能生效一次     | 幂等键、唯一约束、与业务共同提交 | 不同键代表同一业务事件的问题   |
| 数据库与文件最终收敛     | 持久化任务、重试、幂等清理       | 引用关系未定义导致的误删       |

开始写一个接口前，依次明确：业务不变量是什么；会修改几条记录和几种资源；是否可能并发和重试；每个失败点留下什么状态；如何确认、恢复并测试这个状态。
