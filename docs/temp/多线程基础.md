进程 vs 线程

- 进程：操作系统分配资源的基本单位，独立的内存空间
- 线程：进程内的执行单元，共享进程资源
  Chrome 浏览器有多个进程：主进程，网络进程，渲染进程，GPU 进程和插件进程。
  每个进程下有多个线程，例如渲染进程下有：主线程（资源与脚本处理，布局，绘制），合成线程，光栅化线程，工作线程（Web Worker，Service Worker）。

线程的创建限制
Java 的 Thread 不是轻量级协程（不像 Go 的 goroutine 或 JS 的 async function），而是1:1 映射到操作系统内核线程。这就是为什么 Java 线程昂贵、不能无限创建。1.操作系统限制
进程最大线程数：操作系统对单个进程能创建的线程数有上限。例如：
Linux：可通过 ulimit -u 查看用户进程数限制（默认通常 1024~4096），系统全局上限在 /proc/sys/kernel/threads-max。
Windows：无固定上限，但受系统虚拟内存和内核资源影响。2. 内存
每个线程默认会被分配约1M的栈存储空间，例如可用内存3GB，那么理论最大 ≈ 3000 个线程。
与此对比：

- Go 的 goroutine：~2KB 栈起步，可动态增长，百万个没问题
- Java 的 Thread：~1MB 栈固定，几千个就吃力
  Java 21 引入的**虚拟线程（Virtual Thread）**就像 goroutine 的 Java 版本，一个 OS 线程承载多个虚拟线程。
  3.CPU 核心数
  CPU 核心数不直接限制最大可创建线程数（你可以创建几千个线程，但只有少数能并行执行）。但创建远超逻辑核心数的线程会导致频繁上下文切换，降低性能，甚至因资源竞争加剧内存压力。

线程池
创建线程很贵，用完就销毁太浪费。线程池复用一组线程，任务来了直接分配。
内置线程池共有四类：
方法特点newFixedThreadPool(n)固定 n 个线程，无界队列newCachedThreadPool()线程可无限增长，60s 空闲回收newSingleThreadExecutor()单线程，任务按顺序执行newScheduledThreadPool(n)支持定时/周期任务
不推荐使用内置线程池，因为这四类线程池内部使用一个无界的工作队列（LinkedBlockingQueue），容量为 Integer.MAX_VALUE。
当提交任务的速度超过线程池的处理速度时，任务会不断堆积在队列中。由于队列无界，积压的任务数量会持续增长，每个任务（Runnable / Callable）都会占用堆内存。最终，这些堆积的任务会耗尽 JVM 堆内存，导致 OutOfMemoryError: Java heap space
如果要创建线程池，推荐使用 ThreadPoolExecutor 自定义线程池 1.构造方法
ThreadPoolExecutor executor = new ThreadPoolExecutor(
5, // corePoolSize：核心线程数，即使空闲也会保留
10, // maximumPoolSize：最大线程数
60L, // keepAliveTime：非核心线程的空闲存活时间
TimeUnit.SECONDS, // 时间单位
new LinkedBlockingQueue<>(100), // 任务队列
new ThreadPoolExecutor.CallerRunsPolicy() // 拒绝策略
);

// 拒绝策略：
// AbortPolicy：抛异常（默认，适合关键任务）
// CallerRunsPolicy：调用者线程执行（适合普通任务）
// DiscardPolicy：丢弃任务（适合日志等非关键任务）
// DiscardOldestPolicy：丢弃最老任务 2.任务提交
// execute 无返回值
executor.execute(() -> System.out.println("Runnable task"));

// submit 获取返回值，返回值是Future类型
Future<Integer> future = executor.submit(() -> {
Thread.sleep(1000);
return 42;
});
Integer result = future.get(); // 阻塞等待结果 3.生命周期
executor.shutdown(); // 关闭线程池（不再接收新任务，等待已提交任务完成）
try {
// 等待所有任务完成，超时 1 分钟
if (!executor.awaitTermination(60, TimeUnit.SECONDS)) {
executor.shutdownNow(); // 超时则强制关闭
if (!executor.awaitTermination(60, TimeUnit.SECONDS)) {
System.err.println("线程池未正常终止");
}
}
} catch (InterruptedException e) {
executor.shutdownNow();
Thread.currentThread().interrupt();
}
synchronized 线程同步
synchronized 是 Java 中的一个关键字，用于线程同步。它可以保证同一时刻最多只有一个线程执行被保护的代码，从而防止多线程环境下的数据竞争和内存不一致问题。
锁实例方法
锁住的是当前实例对象（this）
//锁住整个对象
public synchronized void increment() {
count++;
}
// 等价于
public void increment() {
synchronized(this) {
count++;
}
}
示例：
public class Counter {
private int count = 0;

    // 同步方法
    public synchronized void increment() {
        count++;
    }

    public synchronized int getCount() {
        return count;
    }

}

// 使用
Counter counter = new Counter();

Thread t1 = new Thread(() -> {
for (int i = 0; i < 1000; i++) {
counter.increment();
}
});

Thread t2 = new Thread(() -> {
for (int i = 0; i < 1000; i++) {
counter.increment();
}
});

t1.start();
t2.start();
t1.join(); //让主线程等t1完成
t2.join(); //让主线程等t2完成

System.out.println(counter.getCount()); // 2000（线程安全）

volatile 轻量级同步
volatile 关键字是轻量级的同步机制，主要用于修饰变量。它保证了两大核心语义：内存可见性和禁止指令重排序，但不保证原子性。

- 内存可见性：当一个线程修改了被 volatile 修饰的变量，新值会立即被强制刷新到主内存（Main Memory）中；其他线程读取该变量时，会强制从主内存中重新读取。
- 禁止指令重排序：编译器和 CPU 为了优化性能，可能会调整代码的执行顺序。 被 volatile 修饰的变量周围会插入内存屏障（Memory Barrier），阻止这种重排序。
- 原子性：一个或多个操作，要么全部执行且执行过程不被任何因素打断，要么就全部不执行。
  虽然 volatile 无锁，很轻量，但它无法替代 synchronized。
  volatile int count = 0;

// 多线程环境下执行 count++，结果会小于预期值！
例如有两个线程同时给count＋1，但执行结果可能为1。流程：
时刻 1（线程 A）：执行第 1 步（读）。此时 count=0，线程 A 读到 0。
时刻 2（线程 B）：执行第 1 步（读）。此时 count 还未被修改，依然是 0，线程 B 也读到 0。
时刻 3（线程 A）：执行第 2、3 步（改+写）。将 0+1=1 写回主内存。由于 volatile 的可见性，主内存变为 1。
时刻 4（线程 B）：执行第 2、3 步（改+写）。关键来了：线程 B 在工作内存中拿的是时刻 2 读到的旧值 0，它对此毫不知情，继续计算 0+1=1，然后将 1 写回主内存。
最终，两次 +1 操作，结果只加了 1。这就是经典的“丢失更新（Lost Update）”问题。
volatile 保证的是：当线程 B 去“读”的那一刻，一定能读到主内存最新值。
Lock 锁（更灵活）
synchronized 是隐式的——JVM 帮你加锁解锁。Lock 是显式的——你自己控制。
ReentrantLock
可重入（Reentrant）是指：同一个线程可以多次获取同一把锁，而不会导致死锁。
具体来说，ReentrantLock 内部维护一个持有计数和持有线程的标记：

- 当线程第一次获取锁时，计数变为 1，并记录持有线程。
- 如果同一个线程再次调用 lock()（例如在同步方法中调用另一个也需要该锁的方法），计数加 1，线程可以继续执行，不会被阻塞。
- 每次调用 unlock()，计数减 1。只有当计数减到 0 时，锁才真正释放，其他线程才能获取。
  import java.util.concurrent.locks.\*;

public class Counter {
private int count = 0;
private final Lock lock = new ReentrantLock();

    public void increment() {
        lock.lock();  // 获取锁，阻塞等待（常用）
        try {
            count++;
        } finally {
            lock.unlock();  // 必须在finally中释放锁
        }
    }

}  
尝试获取锁（非阻塞），若获取不到则执行其他逻辑（如重试、放弃、记录日志），而不是永久阻塞。

    public void tryIncrement() {
        if (lock.tryLock()) {
            try {
                count++;
            } finally {
                lock.unlock();
            }
        } else {
            System.out.println("无法获取锁");
        }
    }

    // 带超时的尝试
    public void tryIncrementWithTimeout() throws InterruptedException {
        if (lock.tryLock(1, TimeUnit.SECONDS)) {
            try {
                count++;
            } finally {
                lock.unlock();
            }
        }
    }

提示：大多数场景下，线程本来就期望等待锁，直接阻塞更简单，因此lock更常用
ReentrantReadWriteLock
虽然 ReentrantLock 是一种强大的独占锁，但它有一个明显的局限：无论读操作还是写操作，都只能有一个线程持有锁。在 读多写少 的场景下，这会造成不必要的串行化，降低并发性能。
ReentrantReadWriteLock 维护了 一对锁。读锁允许多个线程同时持有，写锁同一时刻只能有一个线程持有。相当于可以多个线程读，但同一时刻只能有一个线程写
public class Cache {
private Map<String, String> map = new HashMap<>();
private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
private final Lock readLock = rwLock.readLock();
private final Lock writeLock = rwLock.writeLock();

    // 读操作（多个线程可同时读）
    public String get(String key) {
        readLock.lock();
        try {
            return map.get(key);
        } finally {
            readLock.unlock();
        }
    }

    // 写操作（独占）
    public void put(String key, String value) {
        writeLock.lock();
        try {
            map.put(key, value);
        } finally {
            writeLock.unlock();
        }
    }

}
CompletableFuture 异步编程
Java 8 引入了 CompletableFuture，它实现了 Future 接口。相比于传统的 Future，CompletableFuture 提供了非阻塞的回调链式组合、声明式任务编排和异常处理能力，真正让 Java 的异步编程达到了与 JavaScript Promise 类似的函数式体验。
基本使用
runAsync：异步执行，无返回值
supplyAsync：异步执行，有返回值
import java.util.concurrent.CompletableFuture;

// runAsync 异步执行（无返回值）
CompletableFuture<Void> future1 = CompletableFuture.runAsync(() -> {
System.out.println("Task running");
});

// supplyAsync 异步执行（有返回值）
CompletableFuture<String> future2 = CompletableFuture.supplyAsync(() -> {
return "Result";
});

// 获取结果
String result = future2.get(); // 阻塞
String result2 = future2.join(); // 阻塞（不抛受检异常）
get 来源于 Future 接口，必须处理受检异常。
// get()：必须处理受检异常
try {
String result = future.get();
} catch (InterruptedException | ExecutionException e) {
// 需要显式处理
}
join() 来源 CompletableFuture 自身方法，是非受检异常，可统一处理错误。
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CompletionException;

public class JoinExample {
public static void main(String[] args) {
// 模拟一个可能出错的异步任务
CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
if (Math.random() > 0.5) {
throw new RuntimeException("模拟异常");
}
return 100;
});

        // 链式处理：thenApply 中直接使用 join() 获取结果（示例场景，实际常用 thenCompose）
        CompletableFuture<String> resultFuture = future.thenApply(result -> {
            // 假设这里需要同步获取另一个 CompletableFuture 的结果
            CompletableFuture<Integer> another = CompletableFuture.supplyAsync(() -> result * 2);
            Integer doubled = another.join();  // 使用 join() 无需 try-catch
            return "处理结果: " + doubled;
        });

        try {
            // 最终获取结果：join() 抛出未受检的 CompletionException
            String result = resultFuture.join();
            System.out.println(result);
        } catch (CompletionException e) {
            // 统一处理异步链路中的异常（原始异常可通过 getCause() 获取）
            System.err.println("异步任务失败: " + e.getCause().getMessage());
        }
    }

}
链式调用
thenApply(Function)：接收上一阶段结果，返回新结果（同步）
thenAccept(Consumer)：接收结果，无返回值（最终消费）
exceptionally：发生异常时恢复一个默认值
CompletableFuture.supplyAsync(() -> {
return "Hello";
})
.thenApply(s -> s + " World") // 转换
.thenAccept(System.out::println) // 消费
.exceptionally(ex -> { // 异常处理
System.err.println("Error: " + ex.getMessage());
return null;
});
组合多个异步任务
allOf：等待所有任务完成
anyOf：等待任意一个完成
CompletableFuture<String> future1 = CompletableFuture.supplyAsync(() -> "Task1");
CompletableFuture<String> future2 = CompletableFuture.supplyAsync(() -> "Task2");

// allOf：等待所有任务完成
CompletableFuture<Void> allFuture = CompletableFuture.allOf(future1, future2);
allFuture.join();

// anyOf：等待任意一个完成
CompletableFuture<Object> anyFuture = CompletableFuture.anyOf(future1, future2);
Object result = anyFuture.join();
整型类
AtomicInteger
AtomicInteger是一个线程安全的整型类，它通过 CAS（Compare-And-Swap，比较并交换） 机制和 volatile 内存语义，提供了对 int 值的原子性更新操作
CAS：CAS 是一条CPU 并发原语，它的功能是：“我认为内存位置 V 现在的值应该是 A，如果是，我就把它更新为 B；如果不是，我什么也不做，并告诉我现在的实际值是多少。”，即如果读取的不是期望值，再去内存中去读取值，是一个失败立即重试机制。
方法说明incrementAndGet()原子 +1，返回新值decrementAndGet()原子 -1，返回新值getAndAdd(int delta)原子增加指定值，返回旧值compareAndSet(int expect, int update)如果当前值等于预期值，则原子更新为新值lazySet(int newValue)最终会设置，但稍后可见（性能优化）
public class RequestCounter {
private static final AtomicInteger count = new AtomicInteger(0);

    public void handleRequest() {
        int current = count.incrementAndGet(); // 线程安全，无需加锁
        System.out.println("总请求数：" + current);
    }

}
LongAdder
LongAdder 是 AtomicLong 的升级版，专为写多读少的计数器场景设计。
核心特点：内部通过将单一值分散到多个变量（Cell）上，减少线程竞争，在高并发下性能远超 AtomicLong。
适用场景：统计请求总数、记录访问量等高并发写入的场景。
