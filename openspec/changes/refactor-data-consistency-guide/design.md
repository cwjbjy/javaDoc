## Context

当前 `docs/Spring/database/data-consistency-guide.md`（438 行）是一份数据一致性入门指南，覆盖丢失更新、事务、唯一约束、幂等、跨资源一致性等主题。它采用递进结构（业务规则 → 并发 → 事务 → 唯一性 → 幂等 → 跨资源），以项目中菜品/分类/图片操作为例，混合了通用概念和 MongoDB 特定实现。

目标读者是"会写 Java/Spring/CRUD，但还没系统处理并发、事务和重试"的开发者。当前问题：示例领域（菜品、分类）过于项目特定；MongoDB 语法（`$set`、`$inc`、`MongoTemplate`）对非 MongoDB 用户构成障碍；§8 项目检查表和 §11 版本核验记录快速过时。

## Goals / Non-Goals

**Goals:**

- 将通用概念知识与特定数据库实现分离，使概念层长期可用
- 保留原文的递进结构（业务规则 → 并发 → 事务 → 唯一性 → 幂等 → 跨资源一致性）
- 使用更通用的业务领域（订单、账户、库存）替代菜品/分类/图片
- 移除所有项目绑定内容（§8 检查表、版本核验记录、具体代码文件链接、"当前项目..."注释）
- 新建 MongoDB 实现篇，将原文中 MongoDB 特定的代码示例和配置说明迁移过去
- 概念篇与实现篇之间建立清晰的交叉引用

**Non-Goals:**

- 不编写 MySQL/JPA 实现篇（可作为未来扩展，本次不创建）
- 不修改任何 Java 源码或应用配置
- 不改变原文的核心教学观点和思维框架
- 不为 data-consistency-guide 创建 OpenSpec spec（原文档没有对应 spec，本次也不引入）

## Decisions

### 决策 1：拆分为两个文件而非一个文件内分层

**选择**：创建两个独立 Markdown 文件——`data-consistency-guide.md`（通用概念篇）和 `data-consistency-mongodb-guide.md`（MongoDB 实现篇）。

**替代方案**：在同一个文件内用一级标题分层（上半部分通用，下半部分 MongoDB）。

**理由**：独立文件使概念篇可以独立传播和引用，不会被 MongoDB 内容"污染"。读者不需要滚动过大量 MongoDB 代码才能看到概念。两个文件的维护周期不同——概念层很少变，实现篇随驱动版本更新。

### 决策 2：示例领域选择"订单/账户"

**选择**：使用订单（Order）、账户（Account）、库存（Inventory）作为示例领域。

**替代方案**：保持餐饮领域但抽象化；使用银行转账场景。

**理由**：订单和账户是大多数开发者熟悉的领域，能直接对应"并发修改""唯一约束""幂等"等概念。银行转账虽然经典但过于简化，无法覆盖"跨资源一致性"等复杂场景。订单+库存+账户的组合可以自然覆盖原文所有教学场景。

### 决策 3：概念篇使用伪代码和流程图，不绑定数据库语法

**选择**：概念篇中的代码示例使用伪代码或 Spring Data 通用 API（如 `repository.save()`），不出现 `$set`、`$inc` 等 MongoDB 特定语法。需要展示具体数据库实现时，通过链接指向 MongoDB 实现篇。

**替代方案**：概念篇保留 MongoDB 代码但加注释说明。

**理由**：读者可能使用 JPA/MySQL，看到 `MongoTemplate` 会直接跳过。伪代码足够表达意图，具体实现由实现篇补充。

## Risks / Trade-offs

- **[概念篇过于抽象]** → 通过保留时间线图和流程示意来具象化；每个概念都有"问题场景 → 机制 → 边界"三段式，避免纯理论
- **[MongoDB 实现篇与概念篇脱节]** → 实现篇每个章节开头明确引用概念篇对应章节；概念篇需要具体实现处用 "在 MongoDB 中..." 链接指向
- **[原文读者不适应新示例]** → 核心思维框架不变，只是换了示例领域；目录结构保持一致，方便对照
- **[交叉引用链接失效]** → 使用相对路径；文件名确定后不再变更
