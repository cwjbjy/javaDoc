# 技术指南写作规范

## 核心原则

### 识别内容类型

指南分两种类型，写作前必须先判定：

```
类型 A：渐进式                          类型 B：参考式
════════════════                        ══════════════
知识点有因果链                          知识点是并列的
（问题 → 解决 → 优化）                  （分类 / 清单 / 体系结构）

适合：框架机制、工具使用流程             适合：语言基础、API 体系、概念分类
示例：Spring IoC、MapStruct、           示例：Java 异常机制、集合框架、
     Spring Boot 异常处理                     注解体系

结构：三步走，同一场景贯穿               结构：全景图 → 分类详解 → 进阶 → 实战
```

### 类型 A：渐进式教学（三步走）

同一场景贯穿全文，每步只引入一个新概念。

```
第一层：最简单场景（只需极少注解或零注解）
   ↓
第二层：+ 一个新概念
   ↓
第三层：+ 一个更难的概念
```

### 类型 B：参考式教学

先给出完整知识结构图（全景图），再分类详解每个分支，各分支独立、不强制递进。

```
全景图（完整分类图 / 层次结构图）
   ↓
分支 A 详解    分支 B 详解    分支 C 详解   （并列，互不依赖）
   ↓
进阶概念（仅真正需要递进的内容才用渐进式）
   ↓
实战决策 + 速查清单
```

### 通用原则

**拒绝"参考手册"式平铺**：速查表放附录（最后章节），不在教学主干中以表格形式堆积所有选项。

**概念先于依赖它的语法**：当某语法机制是为处理某概念而设计时（如 `throws` 为受检异常而存在），概念应排在语法之前。若代码注释需要写"（下一节讲）"来前向引用，说明顺序需要调整。

**前置概念先于技术细节**：当理解后续内容依赖于某个先决概念时（如讲 Filter/Interceptor 需先理解 Servlet 容器与 Spring IoC 容器的层次关系，讲 Lambda 需先理解函数式接口，讲 Spring AOP 需先理解切面与横切关注点），这个前置概念必须在任何技术细节之前建立——作为独立的"前置概念"章节（§0），而非埋在某一项技术的介绍中。

> 判定信号：读者如果不先理解这个概念，就无法真正理解后续内容"是什么、为什么、怎么用"→ 需要 §0。

## 结构要求

### 目录

以 Markdown 有序列表开头，包含所有 `##` 标题。

### 类型 A 结构（渐进式）

**§0 前置概念（条件必选）**：当理解这组技术的关键在于某个先决知识时（如两层容器的层次关系、函数式接口的定义、切面与横切关注点的概念），必须在渐进式教学之前插入独立的"前置概念"章节。判定条件见 [通用原则：前置概念先于技术细节](#通用原则)。

每节应有：

- 开篇问题或场景（"为什么需要"）
- 代码示例（通用示例，不绑定项目实际代码）
- 必要时用 ASCII 图解释流程
- 节末简短回顾（一句话或 ASCII 图总结）

### 类型 B 结构（参考式）

- 第 1 节为"全景图"：完整的分类图 / 层次结构图，让读者建立整体认知。这张图即本文的导航地图。
- 第 2 节起为"分类详解"：每个分支独立成节，不强制递进。每节内给出定义 + 代码示例 + 常见变体。
- 进阶概念仅对真正需要递进理解的内容使用渐进式（如异常链：底层 → 包装 → 追溯）。
- 各分支间可加过渡句，但不强制"承上启下"——分支本身是并列的。

### 最后一节（两种类型通用）

统一为"速查清单"，包含 3-5 张 ASCII 表格，覆盖全文关键点。

## 内容规则

### 指南之间不能重叠

在写之前确认：这本指南和已有指南的边界是什么？

原则：区分「是什么」（概念指南）与「怎么用」（操作指南）——概念指南不展开框架细节，操作指南不重复定义概念本身。

以 Java 项目指南为例：

- entity-guide（概念）不讲 @Document/@Entity 注解详解 → 那属于 spring-data-mongodb-guide
- dto-guide（概念）不讲 MapStruct 转换写法 → 那属于 mapstruct-guide

### 文档代码自包含

每篇指南的代码示例必须自包含——读者只看本文档就能理解并运行所有代码。禁止在示例中调用另一篇指南中定义的工具方法、自定义类或常量。

```java
BAD  → 在 spring-filter-interceptor-guide 中调用 buildResponse(...)
        该方法在 spring-exception-guide 中定义，filter 读者找不到它

GOOD → 用内联表达式替代（Map.of()、new LinkedHashMap<>()），
        或在本文档内定义该方法
```

> 判定信号：读者看到某方法调用，在本文档中搜不到定义 → 违规。

### 通用概念优先

```
YES：用多实现横向对比讲同一概念，不绑定单一框架
NO ：以单一框架为主线，其他框架“略”
YES：概念 = 与具体框架无关的本质定义
NO ：概念 = 某框架的注解 / 配置写法

以 Java 数据访问为例：
YES：用三框架对比（JPA / MongoDB / MyBatis）讲 Entity 概念
YES：Entity = 代表数据库记录的 POJO
NO ：Entity = 加了 @Document 注解的类
```

### 不需要的内容

- 项目实际案例（用通用示例）
- "vs 其他方案"对比章节
- 跨指南重复内容
- 框架特有细节放在概念指南中

### 版本一致性

当指南声明适用特定框架版本时（如 "Spring Security 7.x"），**全文所有内容**必须与该版本一致——不仅是个别 API 调用，而是包括：

- **类名**：使用该版本中当前（非废弃）的类名。若需提及废弃类名（如"X 已被 Y 替代"），必须明确标注废弃状态及替换方案
- **架构描述**：Filter 链、组件关系等架构性描述必须反映该版本的实际结构
- **数值引用**：引用源码中的常量值（如 Filter 顺序值）时，必须对照该版本的源码或官方文档验证
- **API 用法**：使用该版本推荐的 API 方式（如 `authorizeHttpRequests()` 而非已废弃的 `authorizeRequests()`）

> 判定信号：读者按指南声明的版本查阅官方文档时，发现类名、行为、数值与指南描述不符 → 违规。

## 写作风格

### 概念先行，定义要完整

```
YES：先解释 CRUD 四个字母分别代表什么，再给代码
NO ：默认读者已经知道 CRUD，直接跳入 save()/findById()
YES：先解释为什么非静态内部类有问题，再说 static 怎么解决
NO ："静态嵌套类不持有外部引用"（没解释为什么这是问题）
```

**外部术语三要素**：指南中引用外部系统的术语（如 MongoDB 的 `$gt`、`$regex`，基础设施术语"副本集"），必须给出：**定义 + 类比（如 SQL 对照）+ 区分生产/开发环境**（如适用）。

### 代码示例要求

- 代码块上方用一句话说明"这段代码在做什么"
- 只使用较新的 API，不包含已废弃的旧版本写法；版本敏感的特性需标注起点版本（如 "MyBatis 3.5+ 起支持"）
- 预览代码也要正确：后文才正式讲的 API，在前文作为"预告"使用时，代码本身必须正确无误
- BAD/GOOD 对比示例中，GOOD 写法必须清晰体现"为什么更好"——不能只展示替代方案，还要让读者一眼看出优势所在
- 代码示例需确保正确性（imports 齐全、流式 API 的 null 安全等基本要求），且**必须通过运行时验证**——不仅要编译通过，还要能正常启动运行。Spring 场景下特别注意：
  - 构造器注入的 Bean 不能同时由同一个 `@Configuration` 类的 `@Bean` 方法定义（会形成循环依赖，应用无法启动）
  - Bean 之间的依赖关系必须可解析（构造器注入不允许形成循环）
  - 代码声称实现的功能必须真正实现（如"注册自定义 Provider"的代码必须真正将 Provider 注册到 Manager，而非仅接收参数后丢弃）
- 示例代码遵循目标语言/框架的最佳实践：不使用魔法数字、优先显式依赖而非隐式注入
  （Java/Spring 额外约定：用枚举常量如 `HttpStatus.NOT_FOUND`，优先构造器注入，禁止 `import foo.*`）
- 方法签名必须**完整可编译**（禁止 `Object body, ...` 等伪代码占位符——读者复制后应直接可用）
- **例子要举全**：代码示例中引用的每个自定义内容——类、接口、枚举、注解、常量、工具方法、自定义异常——必须在同一代码块或更早的示例中给出完整定义。读者看到什么就能理解什么，不需要脑补任何缺失的部分

  ```java
  BAD  → FilterRegistrationBean<MyFilter> 出现了，但 MyFilter 类从未定义
  BAD  → throw new OrderNotFoundException(id) 出现了，但异常类从未定义
  GOOD → 同一个示例中，先定义 MyFilter 类，再定义使用它的 FilterConfig
  ```

- **常见知识点覆盖**：主题下触发条件明确、可在一个示例中讲清的常见 API / 异常 / 变体，每个都在主文中给出具体代码示例——不只在速查清单中列名
- **跨主题简化不断链**：示例涉及外部主题时（如异常处理指南中的 `@Valid`），可省略展开讲解，但必须保留触发效果的最小写法（一行注解、一个配置项），并用提示块指明"属外部主题 + 记住链路"——读者照着示例应能复现文中描述的每个效果

### 类比用简单概念

选用读者熟知的概念做类比，而非同等陌生的概念。以下为 Java 主题示例：

- MapStruct ≈ ES6 扩展运算符的升级版（JS 开发者也能秒懂）
- POJO 历史 → EJB 时代的反抗（用历史背景解释设计动机）

## 写作流程

### 内容类型判定

写作前，根据主题的知识结构判断内容类型，向用户推荐并由用户确认：

```
判定规则：
  · 知识点主体是并列的（分类 / 清单 / 体系结构）→ 推荐类型 B（参考式）
  · 有因果链（问题 → 解决 → 优化）            → 推荐类型 A（渐进式）

示例推荐：
  "Java 异常机制" → 知识点并列（语法、分类、各类异常、Error）→ 推荐参考式
  "Spring Boot 异常处理" → 因果链（try-catch 痛点 → @ExceptionHandler → 自定义异常）→ 推荐渐进式
```

用户确认类型后，进入对应模板。

### 对用户提供优化建议

当用户要求生成指南时，应先在探索阶段提供以下优化建议：

1. 对主题有更好的理解时：提出优化建议
2. 发现有更好的教学方式时：提出调整建议
3. 发现表述不准确时：善意提醒

### 探索期

#### 模型内部自检（不向用户展示）

向用户展示结构草案前，先完成以下自检——这些是模型的职责，用户（尤其新手）无法代劳：

1. **论题自检**：这篇指南要传递的"一个核心洞察"是什么？用一句话写出来。然后检查——每层的示例是否直接支撑这个洞察？

   **判定信号**：如果某层示例可以用另一层技术做得更好，说明示例选错了。

   例（以 Spring Filter/Interceptor 为例）：核心洞察是“Filter 在 Spring 之前、Interceptor 在 Spring 之后”。如果 §1 Filter 示例用计时 → 计时用 Interceptor 更好（能拿方法名）→ 示例选错。

2. **首例核心优势**：§1 的第一个示例是否展示了该技术的**不可替代**价值（只有它能做、换别的技术做不了）？

   **判定信号**：读者看完 §1 会不会问"这用 XXX 不是更好？"如果会 → 换示例。

3. **基础概念排序**：第一个 API 示例之前，理解后续内容所需的心智模型是否已经建立？

   如果核心洞察依赖一个前置概念（如 Filter/Interceptor 依赖"两个容器、两套管理"，Lambda 依赖"函数式接口是什么"），它必须独立成 §0 前置概念章节——不能埋在 §1 内部。

   **判定信号**：读者看到第一个代码示例时，是否已经理解它"在哪个层级运行""为什么这样设计"？如果不知道 → 需要 §0。

#### 向用户展示

自检通过后，向用户展示结构草案（含章节数量和核心主题），确认后再生成。

### 生成后自查

生成完指南后，对照以下清单自查一遍，确认无 bug 再交付：

1. **预览代码正确**：前文作为"预告"使用的后文 API，代码本身是否正确？
2. **版本标注完整**：版本敏感的 API 是否标注起点版本？是否混入旧版本写法？
3. **多实现覆盖**：涉及有多种主流实现的技术点，是否做了横向对比而非绑定单一框架？（Java 数据访问类指南适用：是否覆盖 JPA / MongoDB / MyBatis）
4. **章节连贯**：每节是否有过渡？节末是否有回顾？
5. **BAD/GOOD 对比清晰**：GOOD 写法是否体现了相比 BAD 的优势？
6. **常见知识点覆盖**：速查清单中列出、触发条件明确的常见知识点，正文中是否都有对应的代码示例？代码示例中使用的常见异常 / API，是否在对应详解章节中有正式介绍？有没有只在速查清单列名但正文未展开、或只在代码中使用但从未正式讲解的情况？
7. **概念先于语法**：代码注释中是否有"（下一节讲）""（后文讲）"等前向引用？若有，说明被引用的概念应提前讲解。
8. **全景图完整**（仅类型 B）：第 1 节的全景图是否覆盖了后文所有分支？读者看完全景图能否建立整体认知？
9. **分支独立可跳读**（仅类型 B）：各分类详解节是否相互独立？读者能否从全景图直接跳到任意分支阅读，不需要先读前一节？
10. **主题集中**：速查清单中有独立小节/模板的主题，正文中是否有对应的独立章节？是否有主题在 3+ 个章节中被提及但没有自己的章节？
11. **跨主题示例闭环**：示例涉及外部主题的环节，是否保留了最小触发写法？文中每个可观察效果（Handler 的每个分支、流程图的每条路径、每个"会返回 X"的断言）在示例中是否都有对应的触发端？简化处是否有提示块指明外部主题和链路？
12. **模式一致性**：文中工具方法（如 buildResponse）是否在后文所有 handler 中统一调用？有无某处手写了等价逻辑但未调用同一方法？
13. **跨节逻辑一致性**：后文指出的技术局限性，是否恰好否定了前文的示例选择？
    **判定信号**：§N 说"X 做不了 Y"，而 §(N-1) 的示例恰好依赖 Y → 违规。
    例（以 Spring Filter 为例）：§2 说"Filter 拿不到 HandlerMethod"，但 §1 用 Filter 做方法级日志 → §1 应换成编码 / CORS。
14. **前置概念独立**（仅类型 A）：如果核心洞察依赖一个先决概念，该概念是否独立成 §0 而非埋在 §1 内部？判定信号：读者到 §1 中间才理解"为什么 A 能做 X 而 B 不能"或看到"（后面会讲）"→ 违规。
15. **目录与标题一致**：目录中列出的每个标题是否与正文中对应的标题完全匹配（包括措辞和编号）？锚点链接是否能正确跳转？
16. **版本全局一致**：指南声明的版本下，全文中的类名、架构描述、数值引用是否与该版本一致？是否有已废弃的类名仍被当作当前用法使用？（比第 2 项更强：第 2 项检查单个 API 的版本标注，本项检查全文版本一致性）
17. **代码可运行**：代码示例是否会导致循环依赖、Bean 创建失败等运行时问题？代码声称实现的功能是否真正实现？
18. **事实验证**：引用的源码数值（如 Filter 顺序值）、内部类名、包路径等是否经过对照验证（非凭记忆引用）？

## 反模式

### 结构类

#### 速查表放在教学主干中

```
BAD  → 第四节就是 20 行关键字速查表
GOOD → 第四节用三步递进教学，速查表移至附录
```

#### 话题切换无过渡

```
BAD  → 第三节讲完 Repository 自动 CRUD → 第四节直接开始讲聚合管道
GOOD → 第四节开头："方法命名覆盖 80% 场景，剩下 20% 用 @Query"
```

#### 语法排在概念之前

当某语法机制是为处理某概念而设计时，语法不应排在概念之前。判定信号：代码注释中出现"（下一节讲）""（后文讲）"等前向引用。

```
BAD  → 章节顺序：[依赖概念的语法] → [被语法依赖的概念]
       判定信号：代码注释出现“（下一节讲）”等前向引用

GOOD → 章节顺序：[概念] → [服务于该概念的语法]
       判定信号：每节开头可自然说“上一节讲了 X，Y 正是为它而设计”

以 Java 受检异常为例：
BAD  → 2.2 throw 与 throws（语法）→ 2.3 受检/非受检（概念）
       注释：“IOException 是受检异常（下一节讲）”
GOOD → 2.2 受检/非受检（概念）→ 2.3 throw 与 throws（语法）
       开头：“受检异常必须用 throws 声明——现在来详细讲解”
```

此规则对类型 A 和类型 B 均适用：三步走中若某步依赖后文概念，应调整步骤顺序；参考式中各分支若有概念依赖，被依赖的概念应在前。

#### 前置概念埋在后文中

当下文内容依赖某个先决概念时，这个概念必须在所有技术细节之前独立成章（§0）。不能埋在某一项技术的介绍中——读者要读到中间才恍然大悟"原来如此"。

与「语法排在概念之前」的区别：那条管技术讲解内部的认知顺序（概念 → 依赖它的语法），本条管前置性概念的认知顺序（前置概念 → 后续所有内容）。

```
以 Spring Filter / Interceptor 为例（架构类）：
BAD  → §1 Filter 内部有一节"Servlet 容器 vs Spring 容器"
       读者已读了半个 Filter 才理解"为什么 Filter 不能注入 Service"

GOOD → §0 前置概念独立成章，先讲清楚两个容器、两套管理
       读者带着这个认知进入 §1 Filter → 每一步都知道"为什么"

以 Java Lambda 为例（非架构类）：
BAD  → §1 Lambda 语法内部插入"什么是函数式接口"
       读者看了几页箭头语法，突然遇到这个概念才理解"为什么 Lambda 只能用于单抽象方法接口"

GOOD → §0 先讲清函数式接口的定义和 @FunctionalInterface 注解
       读者带着"Lambda 是函数式接口的实例"的认知进入 §1 → 语法只是表达方式

判定信号：
  · 读者到 §1 中间才真正理解"为什么 A 是 B"或"为什么 C 能做 D"
  · 某个核心知识点在 §1 出现时只能用"（后面会讲）"搪塞
    → 说明该前置概念应提前
```

#### 重要主题散落各处

当一个主题在多个章节中被提及（包括速查清单中有独立小节/模板），但正文没有对应的独立章节时，应将其整合为独立章节。与「常见知识点被精简」互补：后者针对单个项（API/异常/变体）缺代码示例，本规则针对整个主题缺独立章节。

```
BAD  → “自定义异常”散落在 4 个位置：
       - 2.2 节作为子话题（“继承谁”）
       - 3.1 节作为示例（FileOperationException）
       - 4.4 节一句话提及
       - 5.4 节速查清单有完整模板代码
       但没有独立的“自定义异常”章节

GOOD → “自定义异常”有独立章节（第 3 节）：
       - 3.1 为什么需要
       - 3.2 继承谁
       - 3.3 体系设计
       - 3.4 信息设计
       其他章节引用时指向该节
```

**判定信号**：速查清单中有独立小节（如「XX 模板」「XX 速查」）的主题，正文中必须有对应的独立章节。若有 → 检查正文是否已有独立讲解，没有则整合各处内容为独立章节。

#### 工具方法推迟引入

一个会被多个章节复用的工具方法，应在第一次用到时就定义，不推迟到后文"统一介绍"。

```
BAD  → §2 每个 handler 手写 Map.of，注释说"将在 §5 统一介绍"
       §3~§4 继续手写 → §5 终于引入 → 前文已成冗余，返工成本高

GOOD → §2 第一个 handler 直接定义 buildResponse()
       §3 添加重载版本，§4 全部复用，§5 直接引用——零重复
```

**判定信号**：文中出现"将在第 N 节介绍"且 N > 当前位置 → 检查能否提前引入。

### 教学类

#### 定义缺失

不仅本指南的术语需要定义，**引用外部系统的术语**同样不能假设读者知道：

```
以 MongoDB 为例：
BAD  → 直接给 @Query("{ 'price': { $gt: ?0 } }") 示例，不解释 $gt 是什么
BAD  → 直接写“需副本集”，不解释副本集是什么、要不要多台机器
GOOD → 先解释 $gt = 大于（Greater Than），配 SQL 类比：price > 5
GOOD → 先解释副本集 = 主节点 + 从节点，单节点也能跑事务，开发机一条命令搞定
```

**外部术语三要素**：定义 + 类比（如 SQL 对照）+ 区分生产/开发环境（如适用）

#### 流程图/全景图提前引入未定义概念

当流程图或全景图（含 ASCII 架构图、决策树）中出现**本指南主题下的专有概念**（换个框架/模块就不会出现的，如 Spring Security 的 `AuthenticationManager`、Spring MVC 的 `HandlerMapping`），即使只有 1 个，也必须在图出现之前给出定义。

与「定义缺失」的区别：那条规则管正文叙述中的术语定义，本条特指视觉元素（流程图、全景图）中出现的概念——读者看图时无法"跳过去查后文"，图中每个生词都是理解障碍。

```
BAD  → 流程图列出 AuthenticationManager、AuthenticationProvider、
       UserDetailsService 等 Spring Security 专有概念，
       但后文（§2.3）才正式讲解它们
       读者看图时面对多个生词，只能硬着头皮往下读

GOOD → 方案一（1-2 个生词）：图中术语加注脚 / 括号注释
       方案二（多个生词）：图前插入独立"核心模型"小节，
       先定义概念，再展示流程图作为综合回顾
```

**判定标准**：逐个检查流程图/全景图中的每个术语——

1. 该术语是否在**此图之前的正文中**已出现过并给出定义？
2. 该术语是否属于**本指南主题的专有概念**（在其他包/模块中不会使用）？

两项都满足 → 违规，必须在图前给出定义。

> **注意**：通用编程概念（如"接口""线程池""哈希"）和已在 §0 等前置章节定义过的术语不计入。只计算"读者第一次在本指南中遇到的本主题专有概念"。

#### 篇幅与重要性倒挂

```
以 Spring Data 为例：
BAD  → Slice 说“日常开发更常用”但只给 5 行，Page 给了30 行
BAD  → Criteria 是 MongoTemplate 的核心概念但只有一行"Query 是容器"
GOOD → 更重要的概念给更多篇幅：Slice 花 >= Page 的篇幅解释为什么常用、什么场景用
GOOD → 核心 API（Criteria）配上与 @Query 的对照表，说明分工和关系
```

#### 新旧概念之间无桥接

指南中后文引入的 API 如果和前文讲过的是同一件事的不同写法，必须建桥：

```
BAD  → 后文 API 突然出现，读者不知道它和前文讲过的是什么关系
GOOD → “还记得第 N 节的 X 吗？Y 是它的另一种写法：X → Y”

以 Spring Data MongoDB 为例：
BAD  → 第 7 节突然出现 Criteria.where("price").gt(5)，
        读者不知道和第 5 节 @Query("{ $gt: 5 }") 是什么关系
GOOD → “还记得第 5 节的操作符吗？Criteria 是它们的 Java 方法版：
        { 'price': { $gt: 5 } }  →  Criteria.where("price").gt(5)"
```

#### 职责不清不分工

两个类协作但职责不同时，用左右分工表一次性讲清：

```
BAD  → 只说“B 是 A 的容器”，读者不明白为何某方法在 B 上
GOOD → 左右分工表一次性讲清两者各自负责什么

以 Spring Data MongoDB 查询对象为例：
BAD  → “Query 是 Criteria 的容器” → 读者：那 query.limit() 为什么写在 Query 上？
GOOD →
    Criteria（“WHERE”）         Query（“LIMIT / ORDER BY”）
    ───────────────────         ──────────────────────────
    .where("price").gt(5)       .limit(10)
    .and("name").regex(...)     .with(Sort.by(...))
```

#### 危险操作缺反面案例

标注为"危险""容易出错"的行为，必须同时展示安全/危险两种写法：

```
BAD  → 标注“危险”但只给安全写法，读者不知道危险有多严重
GOOD → 安全写法 + 反面案例并列，让读者直观看到“危险”后果

以 MongoDB save() 覆盖文档为例：
BAD  → 只给 findById → setPrice → save 的安全代码
GOOD → 安全做法（findById → 改 → save）
      + 反面案例（new Product() → 只设 id + price → save → 其他字段全丢）
```

#### 正确写法没有体现优势

BAD/GOOD 对比中，GOOD 写法不能只是"换了个写法"，必须让读者一眼看出"为什么这样更好"。如果 GOOD 写法本身含糊不清，读者反而更困惑。

```
以 Java 方法重载为例：

BAD  → 标了“正确 ✅：用方法重载”，但重载内只是把 null 传进去，优势不可见：
       public void updateUser(Long id) { updateUser(id, null); }
       // 读者：这和直接传 null 有什么本质区别？

GOOD → 两个重载各有明确业务含义，末尾一句点明优势：
       // 重载一：不传 name → 明确表达“不更新名字”
       public void updateUser(Long id) { ... }
       // 重载二：传了 name → 明确表达“更新名字，newName 一定非 null”
       public void updateUser(Long id, String newName) { ... }
       // 两个重载各有明确语义，不需要传 null  ← 这句话是 GOOD 的核心
```

**规则**：GOOD 示例必须满足三点——① 有实际业务行为（不是空壳注释）② 展示调用方用法（读者能看到最终体验）③ 末尾一句话点明优势所在。

#### 常见知识点被精简

当主题下存在多个同级别、同频率的常见知识点时，不应为了篇幅而精简掉部分。适用前提：该知识点的触发条件明确，可在一个代码示例中讲清楚。

```
BAD  → 同级别的常见知识点，只选了几个进正文，其余仅在速查清单列名

不适用 → 触发场景过于分散的知识点，不适合用一个示例講清
        → 类层次图中列名 + 速查清单中提及即可

GOOD → 触发条件明确、示例成本低的常见变体，每个都在教学主干中给出
       “触发场景 + 代码示例 + 预防方式”
GOOD → 主文覆盖 80% 日常开发中会遇到的场景，速查清单仅做汇总索引

以 Java 非受检异常为例：
BAD  → 只列 NPE + IllegalArgument，速查清单提到了 ClassCastException 和 ArithmeticException 但无示例
       （两者触发条件明确：强转失败、除零，各一个代码示例就够）
不适用 → IllegalStateException 触发场景分散（“对象状态不对”），不适合单示例讲清
```

**判定标准**（双向检查）：

- 正向：如果某个知识点在“速查清单”中列了名、触发条件明确，但在正文中找不到对应的代码块来演示它 → 违规。
- 反向：如果某个常见异常 / API 在代码示例中被使用了、触发条件明确，但在对应的详解章节中找不到正式介绍 → 违规。

#### 简化导致示例断链

当示例跨越指南主题边界、某环节属于外部主题时，讲解可以简化，但链路上的关键节点不能删。与「指南之间不能重叠」互补：那条管"不展开讲"，本条管"不断链"。

```
BAD  → 异常处理指南：Handler 写了 @ExceptionHandler(MethodArgumentNotValidException.class)，
       流程图也画了这条 400 分支，
       但示例 Controller 没有一个加 @Valid
       → 读者照着做，该分支永远触发不了，“这个 Handler 什么时候有用”成了谜

GOOD → 示例保留最小触发端（参数前加一行 @Valid），
       再用提示块闭环：
       “@Valid 触发校验 → 失败抛 MethodArgumentNotValidException → 落入上面 ③ 号分支返回 400。
        Bean Validation 完整用法是独立主题，这里只需记住链路”
```

**规则**：省的是"展开讲解"（约束注解体系、依赖引入、分组校验），不是"链路节点"（触发端的一行注解）。

**判定信号**：通读全文示例，逐个核对文中承诺的效果——Handler 的每个分支、流程图的每条路径、每个"会返回 X"的断言——在示例代码中是否都有对应的触发方式。缺触发端 → 违规。

### 框架类

#### 绑定单一框架

```
BAD  → Entity 指南全文用 @Document 教学，仿佛 Entity 就等于 MongoDB
GOOD → 三框架对比表 + 核心概念不绑定任何框架
```

#### 声明版本与实际内容不一致

当指南声明适用某个框架版本，但全文的类名、架构描述、数值引用基于旧版本时，会误导读者使用废弃 API。

```
BAD  → 指南声明 "Spring Security 7.x"，但使用 SecurityContextPersistenceFilter
       （6.0 起已废弃，应改为 SecurityContextHolderFilter）
       读者按 7.x 查官方文档时找不到此类名的当前用法

GOOD → 声明 7.x → 全文使用 SecurityContextHolderFilter
       若需提及旧类名（如"7.x 前叫 SecurityContextPersistenceFilter"），明确标注废弃状态
```

**判定信号**：对照指南声明的版本查阅官方文档，发现类名、行为、数值与指南描述不符 → 违规。
